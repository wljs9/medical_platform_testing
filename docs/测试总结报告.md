## 二、接口功能测试(Postman + Newman)

### 2.1 执行方式

- 使用 Postman 构建 Collection(按业务模块分 6 个文件夹)
- 断言覆盖:状态码、响应内容、**数据库一致性**(创建后查 MySQL 确认落库)
- 批量回归使用 Newman 命令行:`newman run xxx.json --env-var base_url=...`

### 2.2 执行结果

- 正向用例 53 条:通过率 100%(不足部分为已发现的缺陷场景)
- 异常场景 8 条:验证出 DEF-005/006/007 等多条缺陷(见第五章)

### 2.3 关键实践

- **接口→数据库一致性校验**:每条写操作后用 SQL 反向验证数据是否真落库
- **批量接口部分失败验证**:通过 count 前后差值定位"无事务回滚"缺陷

## 三、性能测试(JMeter 命令行模式)

### 3.1 测试设计

| 测点 | 接口 | 单请求基线 | 定位 |
|---|---|---|---|
| 轻量计数 | `GET /api/patients/count` | 20ms | TPS 上限基准 |
| 关联查询 | `GET /api/doctors/department/1` | 6ms | 常规查询 |
| 统计聚合 | `GET /api/patients/stats/department` | 305ms | 性能瓶颈重点 |

测试参数:线程 100、爬坡 10s、循环 50 次 = 1.5 万次请求。
采用 **JMeter 命令行模式**(`jmeter -n -t`),避免 GUI 占用资源干扰结果。

### 3.2 结果(100 并发,CLI 模式)

| 接口 | 样本 | 平均耗时 | 90% 线 | 最大 | 错误率 | TPS |
|---|---|---|---|---|---|---|
| `count` | 5000 | 2686ms | 3373ms | 8401ms | 0.00% | 10.81/s |
| `department/1` | 5000 | 2699ms | 3386ms | 8223ms | 0.00% | 10.81/s |
| `stats/department` | 5000 | 3581ms | 4298ms | 9254ms | 0.00% | 10.80/s |

### 3.3 结论与优化建议

1. **统计接口为瓶颈**:`stats/department` 平均耗时(3581ms)比普通查询(~2700ms)高 33%,比单请求基线(305ms)高约 10 倍 —— 根因是 `getDepartmentPatientStats` 对 5 万行 `patient` 全表 `GROUP BY department_id`,**该字段无索引**。建议:加复合索引 → 预期可降至毫秒级。
2. **并发下响应长尾明显**:100 并发时 max 达 8~9s,avg ~2.7s,表明并发升高后连接池/GC 排队。个人开发机 + MySQL 同机环境,结果代表单机能力上限。
3. **GUI vs CLI 对比验证**:同参数下 GUI 模式(受界面资源抢占)错误率 1~3.5%,CLI 模式 0.00% —— 验证了"压测必须用命令行"的官方建议。
4. 所有接口 100 并发下错误率 0%,接口本身无并发一致性错误(如 500/超时),瓶颈主要是**吞吐量限制**。

## 四、接口自动化测试(pytest + requests)

### 4.1 框架设计(分层)

```
config.py        # 环境配置(base_url 等),环境切换只改这里
api/             # 接口封装层,每个模块一个文件(请求细节复用)
testcases/       # 用例层:业务断言 + 缺陷验证
  conftest.py    # fixtures:前置造数 / 后置清理(失败也清理)
pytest.ini       # 标记声明(markers)、运行配置
```

### 4.2 用例设计与结果

| 模块 | 用例 | 结果 | 说明 |
|---|---|---|---|
| 科室 | CRUD 3 条 | ✅ passed | create→get→update→delete 全链路 |
| 科室 | 空名称/重复名/不存在ID 3 条 | 🟡 xfailed | DEF-005/006/007 挂账,修复后自动 XPASS 提醒 |
| 科室 | 批量事务性 1 条 | 🔴 failed | 缺陷:批量无 @Transactional,部分成功未回滚 |
| 患者 | insert / search / update 3 条 | ✅ passed | 覆盖创建、搜索、改信息回归 |
| 患者 | 删除有关联记录的患者 1 条 | 🟡 xfailed | DEF-004:先挂病历再删,验证外键拦截 |

**总计 11 条:6 passed / 4 xfailed / 1 failed(缺陷)。**

### 4.3 工程化要点

- **xfail(strict=True) 管理已知缺陷**:系统缺陷 ≠ 用例失败,黄灯挂账避免狼来了;缺陷修复后自动 XPASS 提醒清理。
- **数据自给自足**:fixture 创建唯一命名数据 + 后置清理,用例可重复执行。
- **断言聚焦正确行为**:只断状态码和关键字段,不依赖不稳定业务数据(吸取 50000 vs 50001 教训)。

## 五、缺陷汇总(共 8 条确认 + 2 条候选)

**严重级别分布**:P1 ×3 / P2 ×4 / P3 ×1(另有新发现候选 2 条)

| 编号 | 标题 | 级别 | 模块 |
|---|---|---|---|
| DEF-001 | 创建接口 gender 枚举契约不一致(DB 存 M/F,接口收中文"男/女",无校验→500) | P1 | 患者/医生 |
| DEF-002 | `id_card char(10)` 存不下 18 位身份证(Data too long→500) | P1 | 患者 |
| DEF-003 | 更新患者接口主键覆盖逻辑风险(可能更新错行) | P1 | 患者 |
| DEF-004 | 删除患者未级联子表,外键 NO ACTION 拦截→500(service 级联代码被注释) | P1 | 患者 |
| DEF-005 | 科室空名称可入库(前后端均无参数校验) | P2 | 科室 |
| DEF-006 | 科室名称无唯一约束,重复可入库 | P2 | 科室 |
| DEF-007 | 查询不存在 ID 返回 200 而非 404 | P3 | 全部 |
| DEF-008 | 异常响应泄露完整 Java 堆栈(SQL/类名/行号暴露) | P2 | 全部 |
| DEF-009(候选) | `with-all-records` 接口疑似 JOIN 串数(无子记录患者返回 1+1) | P2 | 患者 |
| DEF-010(候选) | 批量接口无事务,部分成功不回滚(count 79→82) | P1 | 全部批量 |

## 六、总体结论

1. **功能性**:核心 CRUD 流程可用,但存在**参数校验缺失、外键/数据建模缺陷、批量事务缺失**三类系统性问题,当前质量**不建议直接上线**。
2. **性能**:低并发下表现良好;100 并发时吞吐受限(约 32 TPS),统计接口存在明显索引瓶颈,长尾响应需优化。
3. **测试体系**:已建成「Postman 功能测试 → JMeter 性能测试 → pytest 自动化回归」三层测试能力,缺陷通过 xfail 挂账管理,修复后可自动回归验证。
